# AI Chat 项目 Go 重构最终版 Plan（原始需求，2026-09 用户提供）

> 本文件为原始 Plan 的存档副本（评审基准），正文未做任何改写。

一、项目定位

这是一个轻量的 AI Chat 产品，核心就是：

用户登录 → AI Chat → 塔罗/角色扮演 → 流式回答 → 聊天历史 → 会员和邀请码 → 管理后台

不把项目做成"大而全"的 AI 平台。

二、总体技术架构

前端继续使用 Vue 3。
UI 重构使用 shadcn/ui，并按照统一的 brand-guidelines 进行设计。
后端从 Node.js 重构为 Go。
数据库继续使用 SQLite。
整体采用轻量单体架构：Vue 前端 → Nginx/Caddy → Go API Server → SQLite

AI 单独抽象出来：
Go Chat → AI Provider / Router → Gateway 或官方 DeepSeek API

不拆微服务，不引入 Redis、MQ 等复杂基础设施。

三、AI Gateway 架构

默认采用 Gateway 模式：
Go Chat → 自定义轻量 Router → Bifrost → CPA → 多个免费/低成本模型
Bifrost 尽量负责成熟的 Gateway 能力。
我们自己的 Router 只负责项目真正需要的策略：
模型选择 模型健康状态 首字超时 自动切换 失败处理 最终官方 API 兜底
不自己重新造一个大型 LiteLLM。

四、模型自动切换

CPA 中可以动态汇聚多个模型。
不在 Go 业务代码里面写死具体模型名称。
默认策略：
第一个模型开始请求。
如果大约 2 秒没有收到任何有效首字响应：自动切换第二个模型。
第二个模型仍然没有有效响应：切换第三个模型。
如果三个模型累计大约超过 6 秒仍然没有有效响应：立即切换 DeepSeek 官方 API。
最终目标不是让系统"永远使用免费模型"，而是：能省钱就省钱。但是绝对不能让用户一直等。

五、为什么一定要官方 API 兜底

这是整个方案里非常重要的一层。免费模型只是成本优化方案。DeepSeek 官方 API 是最终保险。
所以用户看到的是：发送消息 → 很快开始响应。即使前面的免费模型挂了，用户也不需要重新发送。
后台自动完成：模型 A → 模型 B → 模型 C → 官方 DeepSeek。用户尽可能无感。

六、Gateway / Official 双模式

系统最终只保留两个 AI 运行模式。
Gateway 模式：Go → Router → Bifrost → CPA → 免费模型池 → 自动 Failover → DeepSeek 官方兜底
Official 模式：Go → DeepSeek 官方 API
这样以后如果：DeepSeek 官方 API 降价 或者免费模型不再值得使用 或者你不想继续使用 CPA/Bifrost
只需要把运行模式切换成 Official。整个系统直接变成：Go → DeepSeek 官方 API
不用重新修改聊天业务。不用重新设计接口。不用把以前的代码再改一遍。
这也是这次重构必须坚持的核心原则：AI Provider 与业务彻底解耦。

七、模型健康机制

后台记录每个模型的基本状态：成功率 失败次数 超时次数 首字时间 完整响应时间 最近错误
某个模型连续失败后：降低优先级或者暂时摘除。过一段时间再自动恢复检测。
避免系统不断请求一个已经挂掉的免费模型。

八、成本控制

正常情况下：优先使用免费/低成本模型。只有免费模型池出现问题时才进入官方 DeepSeek。
后台记录：免费模型请求数量 Gateway 成功数量 模型切换次数 官方 API 兜底次数
以后如果需要，再增加：每日官方 API 兜底预算。
第一版不做复杂的 Token 计费。

九、前端 Chat 用户体验

这次重构重点不是增加大量功能，而是把现有 Chat 做舒服。
必须支持：流式输出。AI 回复过程中可以停止生成。模型自动切换时用户无需重新发送。
Markdown 正常展示。代码块正常展示。AI 回复过程中页面不会乱跳。
用户上滑查看历史时，不强制拉回底部。如果用户本身就在底部，则自动跟随 AI 输出。

十、复制功能

每条消息都提供复制按钮。用户消息可以复制。AI 回复可以复制。
移动端按钮需要足够大，方便点击。这是第一版重点体验优化之一。

十一、移动端输入框

输入框固定在底部。键盘弹出来以后不能遮挡输入框。输入框根据文字自动增高。
超过最大高度后内部滚动。有文字时发送按钮明显可用。
AI 生成时发送按钮变成停止按钮。整体触控区域不能太小。

十二、聊天历史

桌面端：左侧聊天历史。移动端：抽屉式聊天历史。
第一版只做：查看 打开 删除。不做复杂的：搜索 标签 置顶 收藏 分类。保持简单。

十三、用户回答模式

这个和后台角色系统完全分开。用户可以自己选择希望 AI 怎么回答。
第一版主要提供两个维度。
回答长度：精简 适中 详细
回答风格：大白话 标准 专业 严谨 鼓励
实现方式是在系统 Prompt/会话层增加风格要求。不要修改用户原始消息。

十四、角色和 Prompt

目前不增加复杂的后台角色管理系统。也不增加角色热更新。
继续保持现有项目简单的角色/Prompt 逻辑。
以后如果实际运营过程中确实需要管理员直接修改角色和 Prompt，再单独增加。
不要为了"未来可能需要"提前把系统做复杂。

十五、会员

保持现在的简单规则。邀请码固定兑换 30 天。
不做：7 天 90 天 365 天等复杂套餐选择。用户兑换后获得 30 天会员时间。

十六、聊天次数

第一版不限制聊天次数。目前用户量较小，没有必要现在就增加：Token 计费 每日次数 每月次数 复杂套餐 复杂额度系统。数据库结构可以预留未来增加配额的空间。

十七、公告

增加简单的一次性公告。例如管理员发布：系统维护通知 新功能上线 重要提醒。
用户看到并确认后：标记已读。以后不再重复显示。不做复杂公告中心。

十八、Telegram 管理 Bot

保留 Telegram Bot。它就是一个管理员遥控器。
可以做：生成邀请码 查询用户 查看会员到期时间 封禁用户 解封用户 发布一次性公告 开启/关闭注册 开启/关闭邀请码兑换 查看服务状态 查看 Gateway 状态 查看模型健康状态
复杂配置仍然通过 Web 后台。

十九、Telegram Bot 安全

Bot 不直接操作数据库。统一走：Telegram Bot → Go Admin Service → SQLite
只允许指定 Telegram ID 操作。重要管理操作记录日志。

二十、n8n

第一版不依赖 n8n。Go Chat 即使没有 n8n 也必须完整运行。
以后 n8n 可以做：模型故障通知 服务器异常通知 定时统计 运营自动化。但不是核心架构的一部分。

二十一、明确取消：语音

这次最终 Plan 中完全删除语音功能。不做：语音输入 Speech-to-Text Text-to-Speech 语音播放 语音对话 语音相关服务。第一版不为语音增加任何额外基础设施。以后真的有需求，再单独设计。

二十二、明确不做的东西

第一版不做：微服务 Redis MQ 复杂 ORM 复杂支付 复杂会员套餐 Token 计费 BYOK Prompt 市场 Agent MCP 工作区 分享链接 重新生成 答案对比 复杂搜索 标签 收藏 复杂消息管理 复杂智能路由 复杂角色系统 语音功能 n8n 核心依赖

二十四、最核心的设计原则

这次重构真正要做到的不是"增加多少功能"，而是把几个关键问题一次解决。
Node.js → Go：降低资源占用，降低长期维护成本。
DeepSeek 单点 → Gateway：获得多个模型和自动故障切换能力。
Gateway → 官方 API：随时可以切回官方方案。
免费模型 → 官方兜底：降低成本的同时保证用户体验。
代码写死 Prompt → 暂时保持简单：不为了未来需求过度设计。
UI 重构：不追求花哨，而是让 Chat 真正好用。

能复用开源项目的，就不要自己造；现在不需要的功能，就不要提前做；AI 服务可以随时换，但业务代码不能跟着一起改。
